# Устав проекта

> Статус: черновик планирования. Документ фиксирует объём и цели проекта.
> Обновлять при изменении рамок (scope); изменения отражать в разделе «История».

## 1. Назначение проекта

Разработать сервис автоматического построения вариантов подключения
перспективных объектов капитального строительства (ОКС) к существующей
тепловой сети в условиях плотной городской застройки.

Сервис обрабатывает конкурсный набор геоданных, автоматически:
- определяет точки врезки в существующую сеть;
- решает, какие ОКС подключать совместно, а какие раздельно;
- строит новую тепловую сеть с учётом пространственных ограничений;
- рассчитывает расходы и подбирает условные диаметры (Ду);
- проверяет предельные длины участков одного диаметра;
- определяет необходимую реконструкцию существующей сети и камер;
- считает стоимость и формирует до трёх содержательно отличающихся вариантов;
- выгружает результат в один GeoJSON.

## 2. Цели

| № | Цель | Критерий достижения |
|---|------|---------------------|
| Ц1 | Автоматизация процесса | Все перспективные ОКС обрабатываются за один запуск без ручной правки геометрии |
| Ц2 | Корректность расчёта | Соблюдены правила технического приложения (расход, Ду, предельная длина, ограничения, реконструкция) |
| Ц3 | Эффективность решений | Обоснованы число врезок и камер, совместное подключение, объём реконструкции |
| Ц4 | Универсальность | Сервис работает на другом наборе той же структуры без изменения алгоритма и без хардкода данных |
| Ц5 | Объяснимость | Понятные варианты и прозрачное ранжирование по показателю S |
| Ц6 | Готовность к сдаче | Проходит промежуточную и финальную сдачу, есть презентация и сопроводительная документация |

## 3. Объём проекта

### 3.1. Входит в объём (обязательная часть)
- Загрузка одного совмещённого GeoJSON (до 3 ГБ) потоково, без полной загрузки в ОЗУ.
- Преобразование геометрии WGS 84 (EPSG:4326) → WGS 84 / UTM zone 37N (EPSG:32637).
- Разбор всех типов входных объектов и их атрибутов.
- Построение графа существующей сети по `upstream_object_id`.
- Модель пространственных ограничений с правилами «запрет» / «специальный проход».
- Автоматический выбор точек врезки (в камере или в трубопроводе).
- Построение новой сети, в том числе с общими участками для нескольких ОКС.
- Расчёт расходов, подбор Ду, контроль предельной длины.
- Распространение дополнительного расхода к источнику и расчёт реконструкции.
- Расчёт стоимости, штрафов, формирование до трёх вариантов и ранжирование.
- Выгрузка результата в GeoJSON (до 500 МБ); корректность GeoJSON — главный
  показатель качества результата.
- REST API + Swagger UI (springdoc-openapi-ui 1.7.0).
- Сборка и развёртывание через docker-compose; репозиторий с исходниками и
  скриптами деплоя передаётся организаторам.
- Расчёт полностью офлайн, без обращения к внешним сервисам и агентам.

### 3.2. Не входит в объём (границы задачи)
- Полный гидравлический расчёт (давление, потери напора, скорость, насосные режимы, балансировка).
- Расчёт и развитие мощности источника тепла.
- Учёт глубины в обязательной (основной) 2D-задаче.
- Рабочее проектирование, расчёт прочности, конструкция камер и переходов.
- Температурные деформации и компенсаторы.
- Проектная документация и организация строительства.
- Надземная прокладка.
- Определение положения ИТП внутри здания.
- Изменение трассы существующей сети при реконструкции.
- Ручная правка построенной геометрии перед демонстрацией.
- Пользовательский интерфейс (UI): нужен чистый сервис «входные данные →
  выходной GeoJSON»; качество визуализации не оценивается.
- Отдельный контейнер фронтенда: не обязателен и не оценивается.
- Проверка геометрии существующей сети (по протоколу — не проверяется).

### 3.3. Дополнительная задача (Phase 2)
Трассировка с учётом глубины (2.5D) — проектируется и документируется,
реализуется после работоспособной обязательной 2D-части. См.
[docs/04-delivery/roadmap.md](../04-delivery/roadmap.md).

## 4. Заинтересованные стороны

| Сторона | Интерес |
|---------|---------|
| Команда разработки | Работоспособный, поддерживаемый сервис |
| Организаторы кейса (ЛЦТ 2026) | Соответствие правилам, качество трассировки, эффективность |
| Эксперты | Проверка обязательных правил и обоснованности подхода |
| Инженеры-теплотехники | Разумность маршрутов и расчётов |
| Будущие AI-агенты | Однозначный контекст и границы, готовые команды и документация |

## 5. Критерии успеха

1. Промежуточная сдача: прототип загрузки данных, автоматическое построение
   хотя бы части сети, краткий отчёт «реализовано / риски / план».
2. Финальная сдача: работающий сервис, презентация, сопроводительная
   документация, выгрузка результата на конкурсном наборе.
3. Выполнение всех обязательных правил технического приложения.
4. Устойчивость на дополнительном наборе без изменения алгоритма.
5. Корректный выходной GeoJSON (ключевой показатель качества; визуализация
   не оценивается).
6. Быстродействие — дополнительный критерий оценки (жёсткого лимита времени нет).
7. Первый этап оценки — сравнение горизонтальных проекций с эталонной
   геометрией; Z и расчёты углублений — только на втором этапе.
8. Универсальность алгоритма и дополнительные обоснованные критерии стоимости —
   плюс к оценке.

## 7. Условия проведения (по протоколу встречи 16.09.2026)

- Всё решение — на Java 11 (Spring Boot, Spring Data). Kotlin, другая версия
  Spring, C++ и прочие отклонения — риск команды; вариант «внешний контур на
  другом языке внутри Docker» не принимается.
- Сервис разворачивается в единственном экземпляре; горизонтальное
  масштабирование закладывать можно, но не жёстко.
- Ограничений по CPU и времени обработки файла не заявлено; быстродействие —
  дополнительный критерий.
- Расчёт полностью офлайн, без агентов с токенами.
- Команды передают репозиторий с исходниками и скриптами деплоя (Maven и
  Gradle); эксперты разворачивают и проверяют на своих мощностях; для защиты
  команда может развернуть решение у себя.
- Датасет изменён: даётся конкретная точка подключения, геометрия ОКС не
  влияет; объектов — тысячи в масштабе города; часть сведений урезана; реальный
  объём входных данных — до 2–3 ГБ.
- Этапы оценки: (1) сравнение горизонтальных проекций с эталонной геометрией;
  (2) Z-координата и расчёты углублений — до 10 наиболее интересных решений.
