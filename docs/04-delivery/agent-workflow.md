# Работа AI-агентов в проекте

Документ описывает, как агент (opencode и др.) должен входить в проект,
выбирать задачи и завершать их. Цель — стабильный контекст между сессиями.

## 1. Порядок чтения при старте сессии

1. `AGENTS.md` (корень) — краткая точка входа, команды, границы.
2. `docs/index.md` — карта документации.
3. В зависимости от задачи:
   - правила и форматы — `docs/02-domain/`;
   - архитектура/алгоритм — `docs/03-architecture/`;
   - требования и объём — `docs/01-project/`;
   - текущие задачи — `docs/04-delivery/backlog.md`.
4. `source/Протокол встречи 16.09.2026.md` — последние уточнения организатора;
   при расхождениях с ТП уточнения протокола имеют приоритет.

Не начинать реализацию, не прочитав требования (FR/NFR) и правила расчёта.

## 2. Что можно и нельзя

Можно:
- читать/менять исходный код, тесты, конфиги, документацию;
- добавлять ADR и обновлять backlog;
- запускать сборку/тесты/линт.

Нельзя без явного запроса:
- коммитить, пушить, создавать PR;
- менять обязательные версии стека (Java 11 / SB 2.6.3 / springdoc 1.7.0);
- хардкодить координаты, ID и конфигурацию конкурсного набора;
- добавлять внешние сервисы сверх docker-compose;
- удалять/переписывать чужие ADR (только помечать `superseded`).

## 3. Рабочий цикл задачи

1. Выбрать задачу из [backlog.md](backlog.md), отметить `[~]`.
2. Прочитать связанные требования и правила.
3. Реализовать минимально достаточное изменение + тесты.
4. Запустить проверки (см. §4).
5. Обновить документацию и backlog (`[x]`).
6. Кратко отчитаться: что сделано, какие проверки прошли, что осталось.

Одна сессия — одна-две атомарные задачи. Не смешивать несвязанные изменения.

## 4. Команды проверки

```bash
# в оболочке devenv или через `devenv shell --`
mvn -B -DskipTests compile     # компиляция
mvn -B test                    # тесты (без внешней БД)
mvn -B verify                  # полный прогон (может требовать БД)
devenv test                    # smoke окружения
docker compose config          # валидность compose (при изменениях)
```

Перед завершением задачи обязательно: компиляция + тесты.

## 5. Тесты

- Новую логику расчёта сопровождать unit-тестами (см.
  [testing-strategy.md](testing-strategy.md)).
- Тестовые данные — маленькие GeoJSON в `src/test/resources`.
- Тесты детерминированные; не зависеть от порядка выполнения.

## 6. Документация и ADR

- Изменение правил расчёта → обновить `calculation-rules.md`.
- Изменение форматов → `data-model.md`.
- Изменение алгоритма → `algorithm.md`.
- Архитектурное решение → новый ADR (шаблон в `adr/README.md`).
- Изменение объёма → устав и дорожная карта.

## 7. Стиль и соглашения

- Язык документации — русский; идентификаторы — английские
  ([glossary.md](../02-domain/glossary.md)).
- Java 11: не использовать синтаксис новее (records, `var` допустим с 10,
  но избегать для ясности; text blocks недоступны).
- Форматирование — по `.editorconfig`; не добавлять комментарии без пользы.
- Денежные/геометрические расчёты — по ADR-0005/glossary.

## 8. Критерии приёмки

Задача закрывается только при выполнении
[definition-of-done.md](definition-of-done.md).

## 9. Формат отчёта агента (в ответе пользователю)

```
Задача: <ID из backlog>
Сделано: <кратко>
Проверки: <команды и результат>
Документация: <что обновлено>
Осталось: <если есть>
```

## 10. Типичные ошибки (избегать)

- Реализация по `source/data_example.geojson`, а не по ТП (см. риск R-01).
- Хардкод правил ограничений вместо конфигурации (ADR-0009).
- Загрузка всего файла в память (нарушение NFR-08).
- Изменение обязательных версий стека.
- Коммит секретов или больших датасетов.
- Игнорирование протокола встречи и открытых вопросов (NQ-*) при трактовке правил.
- Добавление UI или исходящих сетевых вызовов (нарушение headless/офлайн).
