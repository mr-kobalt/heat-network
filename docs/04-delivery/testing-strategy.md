# Стратегия тестирования

Цель — гарантировать соответствие обязательным правилам и устойчивость
на другом наборе (NFR-09, NFR-10). Тесты должны быть быстрыми и
детерминированными.

## 1. Пирамида тестов

| Уровень | Что проверяем | Инструменты |
|---------|---------------|-------------|
| Unit | Таблицы Ду/стоимости, подбор Ду, предельная длина, формулы стоимости и `S`, правила ограничений, CRS | JUnit 5 |
| Component | Разбор GeoJSON, граф сети, модель препятствий, построение маршрута на малых сценариях | JUnit 5 + JTS |
| Integration | API загрузка→расчёт→выгрузка; работа с PostgreSQL/PostGIS | MockMvc, Testcontainers |
| Golden/E2E | Полный прогон на эталонном наборе, сравнение ключевых показателей | JUnit 5 |

## 2. Обязательные проверки (правила ТП)

- Подбор Ду: для каждого диапазона расхода — ожидаемый минимальный Ду.
- Предельная длина: непрерывная часть одного Ду не превышает лимит;
  камера без смены Ду отсчёт не сбрасывает.
- Предельная длина при смене Ду — новый отсчёт.
- Стоимость участка: `L·cнов·Kгл·Kспец`.
- Врезка в пределах 10 м/≤4 участков → существующая камера; иначе новая.
- Реконструкция: при `Ду_треб ≤ Ду_сущ` не создаётся; иначе стоимость по `cрек`.
- Реконструкция камеры учитывается один раз.
- Штраф: `100e6 + 500000·G`.
- Ранжирование `S` и порядок вариантов.
- Степень камеры ≤4.
- Отсутствие самопересечений новых участков и замкнутых маршрутов.
- Выход: только собственные атрибуты типа; `depth_* = null` в 2D;
  ровно одна `variant_summary` на вариант.
- Увеличение Ду на одну номенклатуру при превышении предельной длины (FR-46, FR-47).
- Нестандартный угол отвода (не 45°/90°) → коэффициент 1,5; минимизация поворотов (FR-57).
- Наложение зон ограничений: максимальный `Kспец`, один спецучасток, без перемножения (FR-54).
- Округление расстояний вверх при незначительном отклонении (FR-58).
- Точка подключения как цель маршрута; геометрия ОКС не влияет (FR-09).
- Камера в каждой точке ветвления; выбор камеры в радиусе 10 м по стоимости (FR-25, FR-71).

## 3. Негативные тесты

- Отсутствуют обязательные поля → понятная диагностика.
- Битые/циклические `upstream_object_id` → ошибка без падения.
- Неизвестный `object_type`/`restriction_type` → диагностика, расчёт продолжается.
- Невалидная геометрия на входе → диагностическая ошибка без падения (протокол).
- Расход превышает максимальную пропускную способность.
- Маршрут не найден для отдельного ОКС → частичный результат.

## 4. Свойства и надёжность

- Детерминизм: одинаковый вход → одинаковый выход (при том же seed).
- Производительность: вход до 3 ГБ, вывод до 500 МБ в пределах памяти.
- Изоляция: сбой одного ОКС не влияет на остальные.

## 5. Соглашения

- Имена тестов: `methodUnderTest_condition_expected`.
- Тестовые данные — маленькие рукотворные GeoJSON в `src/test/resources`.
- Интеграционные тесты с БД — через Testcontainers (`postgis/postgis`).
- Эталонные наборы не коммитить, если они большие; использовать усечённые
  фрагменты и/или внешнее хранилище.
- `mvn test` должен проходить без внешней БД (веб/юнит-срезы).
- `mvn verify` может включать интеграционные тесты.

## 6. Покрытие

Ориентир — не менее 80 % для модулей `hydraulics`, `cost`,
`reconstruction`, `geometry` и конфигурации правил. Для API/склейки —
функциональные сценарии.
