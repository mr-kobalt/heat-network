# Архитектура (обзор)

## 1. Контекст (C4, уровень 1)

```
┌──────────────┐   GeoJSON (до 3 ГБ)   ┌───────────────────────────┐
│ Пользователь │ ────────────────────▶ │  Heating Routing Service  │
│ (инженер)    │ ◀──────────────────── │  (Spring Boot, Java 11)   │
└──────────────┘   результат GeoJSON    └────────────┬──────────────┘
                                                     │ JDBC
                                                ┌────▼─────────────┐
                                                │ PostgreSQL+PostGIS│
                                                └──────────────────┘
```

Пользователь (до 50 одновременно) загружает набор, запускает расчёт,
получает результат для скачивания. Документация API — Swagger UI.

> По протоколу встречи: UI не требуется — это **headless-сервис**
> «входные данные → выходной GeoJSON»; качество визуализации не оценивается,
> важна корректность GeoJSON. Сервис работает **офлайн** и разворачивается
> в **единственном экземпляре** (горизонтальное масштабирование —
> опционально). Swagger/сопроводительная документация API — желательны.
> Отдельный контейнер фронтенда не нужен.

## 2. Контейнеры (C4, уровень 2)

| Контейнер | Технология | Ответственность |
|-----------|-----------|-----------------|
| `app` | Spring Boot 2.6.3, Java 11 | REST API, конвейер расчёта, формирование GeoJSON |
| `db` | PostgreSQL + PostGIS | Хранение метаданных датасетов/расчётов |
| `frontend` (опц.) | React + MapLibre (nginx) | Визуализация результата, локальная карта Москвы и области (PMTiles), профиль compose `frontend` (ADR-0013/0028) |
| Swagger UI | springdoc-openapi-ui 1.7.0 | Документация API |

Сборка/запуск — docker-compose 1.29.2 (`docker-compose.yml`).

```

                                                        │
                                                        ▼
                                              variants ──▶ output
                                                        ▲
                                                   persistence
```

| `ru.lct.heating.graph` | Топология существующей сети по геометрии, примыкания камер |
| `ru.lct.heating.routing` | Кластеризация ОКС, присоединение через камеру, маршруты; подключаемые алгоритмы трассировки (`routing.algorithm`, ADR-0027) |
| `ru.lct.heating.hydraulics` | Расходы, подбор Ду, предельные длины по путям |
| `ru.lct.heating.cost` | Единая модель стоимости и коэффициенты |

## 4. Поток данных

1. **Загрузка.** Файл принимается потоково во временное хранилище (FR-07).
2. **Разбор.** `ingest` читает поток, классифицирует объекты, проверяет
   обязательные поля, преобразует геометрию в EPSG:32637.
3. **Существующая сеть.** `graph` строит топологию по геометрии (смежность
   участков, примыкания камер).
4. **Препятствия.** `geometry` готовит запретные зоны (буферы), спецзоны и
   финальный коридор в `oks`-полигоне; правила — конфигурируемые (ADR-0009).
5. **Маршрутизация.** `routing` кластеризует точки подключения, выбирает
   присоединение через камеру, строит маршруты, назначает спецпроходы
   (эвристика, ADR-0006). Алгоритм трассировки выбирается при запуске:
   `POST /api/v1/datasets/{id}/runs?algorithm=<id>` (по умолчанию `grid-forest`,
   ADR-0027); список доступных — `GET /api/v1/algorithms`.
6. **Гидравлика.** `hydraulics` суммирует расходы, подбирает Ду совместно с
   предельной длиной по непрерывным путям.
7. **Стоимость.** `cost` считает стоимость участков, камер, врезок в
   существующие камеры, штрафов.
8. **Варианты.** `variants` формирует до трёх вариантов и рассчитывает `S`.
9. **Вывод.** `output` пишет единый GeoJSON.
10. **Этапы (опционально).** При `?trace=true` `trace` сохраняет промежуточные
    данные этапов в `runs/<id>/stages/` (`GET /api/v1/runs/{id}/stages`,
    ADR-0036); без флага конвейер работает как раньше.

## 6. Границы

- Полный гидравлический расчёт и мощность источника не реализуются.
- Реконструкция существующей сети и камер не выполняется (ТП v2).
- Обязательная часть — 2D; глубина — отдельный необязательный режим (Phase 2).
- Готовая геометрия не правится вручную.
- Внешние ГИС/сервисы не используются; всё локально в контейнерах, офлайн.
- UI не разрабатывается (headless-сервис).
- Два этапа оценки: горизонтальные проекции, затем Z/глубины (до 10 решений).
