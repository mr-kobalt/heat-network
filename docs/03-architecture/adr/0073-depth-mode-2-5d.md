# ADR-0073. Режим с учётом глубины (2.5D)

- Статус: accepted
- Дата: 2026-09-29

## Контекст

ТП v2 §5 задаёт необязательный дополнительный режим с учётом глубины:

- отдельный режим и **отдельный набор вариантов**, не объединяемый с 2D; результат
  режимов в одно ранжирование не сводится; Z-координаты не требуются;
- вертикальное положение — атрибуты `depth_start`/`depth_end` (метры до верхней
  границы расчётного габарита новой сети);
- условная горизонтальная поверхность: обычная глубина 3,0 м, минимальная 0,7 м,
  максимальная глубина и дискретный шаг не задаются;
- профиль при необходимости изменения глубины: спуск/подъём, участок постоянной
  глубины, при необходимости возврат; уклон ≤ 0,10 м/м (на 1 м глубины ≥ 10 м по
  горизонтали); между близкими препятствиями допускается сохранять изменённую
  глубину;
- для стоимости и предельной длины — длина по горизонтальной проекции;
- `Kгл = 1` при `h ≤ 3,0`; `Kгл = 1 + 0,10·(h − 3)` при `h > 3,0`; на участке
  спуска/подъёма — среднее арифметическое `Kгл` в начале и конце;
- при пересечении уровня 3,0 м создаётся `technical_node` и участок делится.

FR-90…FR-93. Источник — ТП v2 §5; разъяснение 16.

## Решение

1. **Режим — параметр запуска.** `POST /api/v1/datasets/{id}/runs?mode=2d|depth`
   (по умолчанию `2d`). Значение сохраняется в `calculation_run.mode` и
   возвращается в `RunResponse.mode`. 2D-ветка не меняется: без `mode=depth`
   результат идентичен прежнему (baseline сохраняется).

2. **Глубина — вертикальный пост-слой над 2D-планом (первый шаг).** Маршрут
   `grid-forest` строится как обычно; затем для каждого ребра вычисляется
   вертикальный профиль. ТП не обязывает строить маршрут заново, поэтому
   переиспользование 2D-трассы допустимо и снижает риск. Интеграция глубины в
   поиск пути (2.5D-состояние) — отдельная последующая задача.

3. **Модель профиля** (`ru.lct.heating.depth`):
   - вертикально значимые спецпроходы берутся из `SpecialZoneIndex` по типу
     ограничения с заданными вертикальными габаритами (таблица 4 ТП +
     допущение ADR);
   - габарит новой сети — высота по таблице 1 для её Ду; зазор до коммуникации —
     `heating.app.depth-vertical-clearance-m` (допущение, ТП чисел не даёт);
   - при конфликте с отметкой 3,0 м выбирается проход сверху (до `depth-min-m`)
     либо снизу; предпочтение — вариант с меньшим `Kгл`; границы — спуск/подъём с
     уклоном ≤ `depth-max-slope`, полка на постоянной глубине;
   - близкие пересечения (зазор ≤ `depth-close-crossing-m`) объединяются без
     возврата на 3,0 м (закрывает NQ-05 допущением);
   - точки пересечения уровня 3,0 м и границы полок — `technical_node` и деление
     участка (FR-30: смена параметра без разветвления);
   - `depth_start`/`depth_end` — на итоговых `OutputSegment`; для полки `Kгл(h)`,
     для спуска/подъёма — среднее `Kгл` концов.

4. **Стоимость и ранжирование.** `Kгл` подаётся в существующий
   `CostModel.segmentCost(..., depthCoefficient, ...)`; `S` и ранжирование
   считаются от стоимости режима глубины. Наборы 2D и глубины не смешиваются
   (разные запуски/файлы).

5. **Конфигурируемость (ADR-0009).** Параметры `heating.app.depth-*`; вертикальные
   габариты — в правилах ограничений (`heating.restrictions.rules.<type>`:
   `vertical-top-depth-m`, `vertical-height-m`) только для типов, у которых они
   заданы ТП (`gas_pipeline` — 2,8/0,40; `power_cable` — 2,7/0,20;
   `heat_network` — 3,0/высота габарита).

## Следствия

- Положительные: отдельный режим и отдельный вывод по ТП; обязательная 2D-часть
  не затрагивается; вертикальная модель изолирована и тестируема.
- Отрицательные: ТП не задаёт числовой вертикальный зазор и критерий «близких»
  препятствий — введены конфигурируемые допущения; профиль считается по ребру, а
  не по непрерывному пути дерева (на границах рёбер — возврат на 3,0 м), что
  может быть уточнено при интеграции в поиск.
- Неизвестные вертикальные габариты типов не учитываются (диагностика).
