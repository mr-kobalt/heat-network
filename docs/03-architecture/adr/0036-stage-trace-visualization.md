# ADR-0036. Поэтапная трассировка для визуализации

- Статус: accepted
- Дата: 2026-09-22

## Контекст

Визуализатору (ADR-0013, ADR-0028) для разбора и демонстрации работы алгоритма
`grid-forest` нужны промежуточные данные этапов: выбор точки выхода, маска
проходимости, деревья по проходам поиска, уточнение геометрии (`refine`) и
переподключение терминалов (`relink`). Сейчас конвейер считает эти данные, но
нигде не сохраняет: `CalculationService` держит стадии локальными переменными,
`GridForestPlanner` — маску, клетки, деревья и кандидатов relink только в
памяти; наружу отдаётся лишь итоговый GeoJSON. Ядро при этом должно оставаться
headless (ADR-0010), а боевой расчёт — не замедляться и не раздувать storage.

## Решение

Ввести **opt-in трассировку** промежуточных этапов, не влияющую на результат.

1. **Активация.** Трассировка включается флагом запроса
   `POST /api/v1/datasets/{id}/runs?trace=true` (по умолчанию `false`) и
   хранится в `calculation_run.trace`. Без флага используется no-op
   `StageTrace.disabled()` — ветвления трассировки не меняют ни геометрию, ни
   детерминированность, ни baseline `S`.

2. **Захват.** `StageTrace` (пакет `ru.lct.heating.trace`) — аккумулятор
   этапов в памяти. Общий конвейер добавляет этапы `network`, `obstacles`,
   `special`, `exits`; `GridForestPlanner` — `grid` (маска, источники, клетки
   входа), `trees-<проход>` (сырые отрезки сетки до сглаживания), `relink`
   (после `TerminalRelinker`, сырая геометрия) и `refine` (финальная геометрия
   после string pulling и ремонта поворотов; ADR-0038) для лучшего прохода.

3. **Формат.** Писатель `StageTraceWriter` кладёт в `data/runs/<id>/stages/`:
   `manifest.json` (упорядоченный список вкладок и проходов), по одному
   `*.geojson` на геометрический этап (`network`, `obstacles`, `special`,
   `exits`, `trees-N`, `relink`, `refine`) и `grid.json` с растровой маской.
   Геометрия конвертируется в EPSG:4326 (`CrsTransformer`); маска передаётся
   base64-битсетами запретов и достижимых клеток (строка 0 — север), при
   превышении `trace-grid-max-pixels` — консервативное прореживание. Компактная
   битовая маска выбрана вместо GeoJSON-клеток (объём) и серверных PNG-тайлов
   (сложность), ADR-0033/0034.

4. **API.** `GET /api/v1/runs/{id}/stages` — манифест;
   `GET /api/v1/runs/{id}/stages/{stageId}` — этап GeoJSON (для `grid` —
   JSON-маска). Идентификатор этапа валидируется и не выходит за каталог.

5. **Область.** Этапы поддерживает только `grid-forest` (ADR-0034/0035) — через
   default-перегрузку `TracingAlgorithm.plan(..., StageTrace)`. `mst` остаётся
   без изменений.

6. **Фронтенд.** Визуализатор показывает переключатель вкладок
   «Вход → Сеть → Ограничения → Спецпроходы → Выходы → Сетка →
   Деревья (#проход) → Переподключение → Refine → Итог»; данные этапа
   подгружаются по требованию. `grid` рисуется как изображение из битсета
   (image-слой MapLibre) по четырём WGS84-углам.

## Следствия

- Положительные: объяснимость и отладка алгоритма на карте; ядро headless,
  трассировка выключена по умолчанию; результат и baseline не меняются; объём
  масок ограничен budget-параметром.
- Отрицательные: новый диагностический контракт и файлы рядом с результатом;
  при включённой трассировке расходуется ОЗУ под снапшоты и диск под
  `stages/`; поддержка новых этапов требует правок писателя и фронтенда.
- Затрагивает `TracingAlgorithm` (аддитивная default-перегрузка),
  `VariantGenerator`, `CalculationService`, `GridForestPlanner`,
  `ObstacleMask`/`ObstacleIndex` (аксессоры), `RunController`/`RunService`,
  схему `calculation_run`.
