# ADR-0050. Контракция сквозных (degree-2) узлов в grid-forest

- Статус: accepted
- Дата: 2026-09-24
- Контекст: FR-30, ADR-0044, `technical_node` в выводе

## Контекст

По ТП v2 / FR-30 технический узел (`technical_node`) создаётся **только** при
смене параметра без разветвления (способ прокладки, профиль глубины, Ду и
т.п.); обычный поворот узла не требует. Однако в выводе `grid-forest`
появлялись многочисленные `technical_node` степени 2, у которых оба инцидентных
участка совпадали по `diameter` и `laying_method` — то есть «узлы» стояли на
обычных вершинах ломаной.

### Причина

`GridForestPlanner.buildTree` создаёт узлы только в точках ветвления/корне/
терминалах (степень ≥3, 1 или лист), поэтому сквозных degree-2 узлов в дереве
нет. Но `TerminalRelinker.rebuild` (`TerminalRelinker.java:651-662`) назначает
тип узла по степени:

```java
} else if (node.getId().equals(rootId) || degree >= 3) {
    type = NodeType.CHAMBER;
} else {
    type = NodeType.TECHNICAL_NODE;   // степень 2 → «технический узел»
}
```

При переприсоединении терминалов и обрезке тупиковых ветвей бывшие развилки
теряют ветви и их степень становится 2 — они помечаются `TECHNICAL_NODE`.
Далее `ForestResultBuilder` выпускает такие узлы, и каждый из них разрывает
`LineString` на два участка. На основном наборе это давало 4–7 лишних узлов в
варианте, на наборе OSM (strict) — 23–41.

Узлы, создаваемые `ForestResultBuilder` по границам `SpecialSpanSplitter`
(`*_tech_*`), корректны: у них всегда меняется `diameter` или `laying_method`.

## Решение

После `relink` и **до** фиксации этапов/`refine` выполняется контракция
сквозных узлов деревьев (`GridForestPlanner.contractPassThroughNodes`, fixpoint):

- контрактируется узел, если он `NodeType.TECHNICAL_NODE`, `!isExisting`,
  не корень, степень ровно 2 и оба инцидентных ребра имеют одинаковый
  `diameterMm`;
- два ребра склеиваются в одну `LineString` (ориентация приводится к общему
  узлу), узел удаляется; повтор до стабилизации (схлопываются цепочки).

Сохраняются: корень, терминалы, существующие и планировочные камеры, а также
degree-2 узлы со **сменой Ду** (это законный `technical_node`, и
`MaxLengthEnforcer` работает уже после контракции). Геометрия не меняется:
удалённый узел остаётся внутренней вершиной объединённой полилинии, поэтому
`checkTurns`/`turnsWithinLimit` продолжают его видеть.

## Следствия

- Положительные: `technical_node` соответствует FR-30 (только смена
  параметра); меньше фиктивных узлов и разрывов `LineString`; trace
  (`relink`/`refine`) согласован с выводом.
- Отрицательные/ограничения:
  - меняется baseline основного набора: `S` 13.580152442677246 →
    `13.560621677285116`, длина 1913.479 → 1910.365 м, стоимость
    → 279 625 973 ₽ (эталоны `CalculationPipelineSlowTest` пересчитаны);
  - на основном наборе `technical_node` в выводе более не остаётся (нет смены
    Ду без разветвления); на OSM остаются только узлы границ спецпроходов;
  - объединённые рёбра длиннее по числу вершин (регресс-порог 15 сохранён:
    факт. максимум 11).

## Проверка

`GridForestPlannerContractionTest` (fast: цепочка, обратная ориентация, смена
Ду, существующая камера, точка на пути) и
`TechnicalNodeInvariantSlowTest` (основной + OSM: нет degree-2 `technical_node`
с одинаковыми `diameter`/`laying_method`). Slow-набор и инварианты
FR-26/FR-29/FR-34 — без регрессий.
