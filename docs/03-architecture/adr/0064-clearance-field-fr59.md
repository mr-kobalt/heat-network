# ADR-0064. Clearance-поле и «векторный» движок для FR-59: отклонено

- Статус: rejected
- Дата: 2026-09-28

## Контекст

Рассматривалось предложение построить маршрутизацию на векторном
топологическом графе (visibility graph / NavMesh) с локальной верификацией
зазоров (clearance), иерархической разбивкой (quadtree/H3), сжатием графа
(contraction hierarchies / hub labels), MST по Делоне и движком pgRouting
поверх PostGIS. Отдельная ценная часть — **clearance-поле**: заранее посчитать
для клетки/ребра «бутылочное горлышко» (расстояние до препятствия) и пускать
трассу по фактическому/оценочному Ду, вместо повторной пересборки буферов.

Проблема, которую это должно решать, реальна: в дефолтном режиме запретные
буферы считаются по **минимальному** Ду (ADR-0037), а фактический Ду зависит от
расхода ниже по дереву (FR-41/43/48) и задаёт габарит (FR-51/59). То есть
соответствие FR-59 в дефолте не гарантируется (E16). Post-hoc DN-aware ремонт
рёбер отклонён (ADR-0063) — почти все рёбра идут у границы буферов мин. Ду.

## Что проверялось

Прежде чем строить clearance-поле, измерен уже реализованный
**проактивный** DN-aware режим `forest-diameter-aware-buffers=true`: индекс
пересобирается по максимальному фактическому Ду варианта и расчёт повторяется
(`CalculationService.generateVariants`). Это более сильное вмешательство, чем
clearance-поле: трасса реально перекладывается под фактическую ширину, а не
только ускоряется проверка. A/B через `VerificationHarnessTest`:

| Набор | Режим | `S` | Длина, м | Повороты >90° | Exit mismatch |
|-------|-------|----:|---------:|--------------:|--------------:|
| Скорректированный | baseline | 13.4250 | 1913.09 | 0 | 0 |
| Скорректированный | DN-aware (`usedDn=300`) | 13.5759 | 1997.26 | **16** | **1** |
| OSM | baseline | 13.7609 | 1985.22 | 1 | 0 |
| OSM | DN-aware (`usedDn=300`) | 13.5999 | 1862.96 | **20** | **1** |

Сходимость — 1 итерация (`usedDn=300 candidateDn=300`). На OSM `S` даже
улучшается (длина −122 м), но оба набора получают десятки нарушений FR-34.

## Решение

Отклонено. Ключевые причины:

- **Блокер — геометрия, а не вычисления.** DN-aware перекладка рушит ремонт
  геометрии `refine` (микро-вершины/шипы у выходов, angle 150–176°). Clearance-
  поле — лишь быстрый эквивалент `ObstacleIndex.isInteriorBlocked` по фактическому
  Ду; оно не меняет вердикт точной проверки и потому не устранит эти нарушения.
- **Основная цена — не `buffer()`.** В `generate` доминирует повторный прогон
  планировщика (~5 с на проход), а не построение буферов (~0.4 с). Разделяемое
  по Ду clearance-поле сэкономило бы лишь малую часть.
- **Обратная связь не причинна.** Ду ребра определяется снизу вверх по дереву;
  в прямом проходе роста он ещё неизвестен. Единый width-aware Дейкстра без
  итерации невозможен, а итерация уже реализована и регрессирует.
- **Прочие части предложения не подходят к задаче** и уже рассмотрены:
  visibility-граф как движок — superseded (ADR-0031 → ADR-0034, попарные
  проверки); Delaunay/MST по точкам — старый `mst` и ANE-MiST (ADR-0048);
  контракция degree-2 уже есть (ADR-0050); CH/hub labels решают статические
  many-to-many, тогда как нужен один multi-source Дейкстра по плотной сетке
  (офлайн, без жёсткого лимита времени, NFR-08); pgRouting не выражает
  доменные ограничения (камеры/степень, спецпроход одним прямым участком,
  изоляция своего ОКС) и добавляет round-trips.

Флаг `forest-diameter-aware-buffers` остаётся **выключенным**; E16/FR-59 —
известный разрыв дефолта. Clearance-поле как самостоятельная оптимизация не
строится.

## Следствия

- Положительные: не тратится время на движок без измеримого выигрыша; сохранены
  детерминизм, офлайн и отлаженный конвейер (ADR-0033…0063).
- Отрицательные: FR-59 в дефолтном режиме по-прежнему не гарантируется;
  возврат к теме требует нового ADR и, вероятно, переработки геометрического
  ремонта под фактический Ду.
- Прежний положительный эффект clearance («узкий коридор») реализован точечно
  для терминалов — ADR-0065.
