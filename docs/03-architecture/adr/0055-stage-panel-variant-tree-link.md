# ADR-0055. Этапы расчёта в левой панели, связь вариант↔дерево и постадийная трасса

- Статус: accepted
- Дата: 2026-09-25
- Контекст: ADR-0036, ADR-0037, ADR-0050, ADR-0051, ADR-0053

## Контекст

Визуализатор (ADR-0013, ADR-0028, ADR-0036) показывал этапы алгоритма
горизонтальной лентой в шапке сайта. После ADR-0044…0054 конвейер `grid-forest`
обогатился шагами (re-link топологии, контракция сквозных узлов, refine,
оптимизация положения камер/корня), которые полезно видеть отдельно, но лента в
шапке перестала вмещать и читаться. Кроме того:

- этапы после «Деревьев» (`relink`, `refine`) записывались только для
  **лучшего** прохода (ADR-0036/0038), поэтому при выборе другого дерева карта
  показывала чужие действия;
- переключатель «Вариант» и выбор прохода «Деревьев» были независимы, хотя
  вариант — это и есть результат отдельного прохода поиска (ADR-0037).

## Решение

1. **Левая панель — вертикальные вкладки.** Шапка освобождается от этапов.
   Навигация визуализатора: `Данные` (вход + сводка вариантов), `Этапы`
   (вертикальный список этапов) и `Слои`. Этапы отображаются вертикально,
   с иконками и подсветкой активного шага.

2. **Постадийная трасса per-pass.** `StageTrace` хранит снимки по каждому
   проходу: `trees-N`, `relink-N`, `contract-N`, `refine-N`, `chambers-N`
   (ADR-0036/0050/0051/0053). `StageTraceWriter` пишет файлы `<id>-<N>.geojson`,
   а в манифесте у соответствующей стадии появляются `passes` и `bestPass`.
   Фронтенд грузит стадию по выбранному проходу (`relink-2`, `refine-1`, …) через
   общий `stageFileKey`.

3. **Дополнительные этапы.** Добавлены `ties` (кандидаты врезки), `contract`
   (контракция сквозных degree-2 узлов и ориентация от корня) и `chambers`
   (оптимизация положения новых камер/корня). Итоговый порядок: Вход → Сеть →
   Ограничения → Выходы → Кандидаты врезки → Сетка → Деревья → Relink →
   Контракция → Refine → Камеры → Итог.

4. **Связь вариант ↔ дерево.** В сводку варианта (`variant_summary`) пишется
   номер прохода `pass`, из которого выращен вариант. Визуализатор строит
   двустороннюю карту `variantToPass`/`passToVariant`: выбор варианта меняет
   активное дерево и наоборот. Проходы, не породившие вариант (дедупликация
   проходов, ADR-0037), не меняют текущий вариант.

5. **Границы.** Трассировка остаётся opt-in (`?trace=true`), на результат и
   baseline `S` не влияет: при выключенной трассировке снимки — ссылки на те же
   списки (`trace.isEnabled()`), геометрия не меняется. Постадийные снимки
   увеличивают объём `stages/` и ОЗУ при включённой трассировке.

## Следствия

- Положительные: шаги после «Деревьев» соответствуют выбранному дереву;
  варианты и деревья переключаются согласованно; наглядность новых улучшений
  конвейера.
- Отрицательные: `stages/` растёт (×число проходов на стадии); число файлов
  манифеста больше; при новом этапе нужны правки `StageTraceWriter`, манифеста и
  фронтенда.
- Затрагивает `StageTrace`, `StageTraceWriter`, `GridForestPlanner`,
  `ForestPlanningResult`, `VariantGenerator`, `ForestResultBuilder`,
  `VariantSummary`, `GeoJsonResultWriter`; фронтенд — `store`, `types`,
  `StagePanel`, `StageDataLoader`, `MapView`, `stageLayers`.
