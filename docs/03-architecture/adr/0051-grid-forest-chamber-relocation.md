# ADR-0051. Оптимизация положения новых камер (медиана соседей + прямая перепрокладка стыков)

- Статус: accepted
- Дата: 2026-09-24
- Контекст: FR-30, ADR-0035/0046 (E35), ADR-0044, ADR-0049

## Контекст

Положение новых камер в `grid-forest` определяется ростом по сетке от сети
(meeting-point волн Дейкстры) и после `relink`/`refine` уже допустимо, но не
оптимально по стоимости: узел-развилка может стоять не в «точке с минимальной
суммой линий подключения» (геометрической медиане соседей). E35 оптимизировал
только точку врезки **корня** (перпендикулярная проекция на сеть). Для
ветвящихся камер аналогичной оптимизации не было.

Оценка по текущему выводу: верхняя (евклидова) экономия суммы длин инцидентных
рёбер по медиане соседей — ~36–45 м на вариант (основной и OSM-наборы).

## Решение

Новая стадия `GridForestPlanner.optimizeChambers` (флаг
`forest-chamber-optimization`, по умолчанию **вкл**), выполняется после
`refineTrees` (и до `estimateScore`). Перемещаются **все новые камеры**
(`type == CHAMBER && !existing`), включая корень; существующие камеры и точки
подключения фиксированы, топология не меняется.

1. **Кандидаты позиции.** Для не-корневых камер — взвешенная геометрическая
   медиана (Вейсфельд, веса `нов(Ду)`) координат соседних вершин инцидентных
   рёбер; далее свободные клетки в радиусе `forest-chamber-search-radius-cells`
   вокруг медианы (предел `forest-chamber-max-candidates`). Для корня — проекции
   на существующую сеть (`candidateProvider.projections`), т.е. привязка к сети
   сохраняется (логика E35 внутри стадии).
2. **Перепрокладка стыков.** Стык «камера → соседняя вершина» заменяется
   **прямым отрезком** (как при string pulling в `refine`). Кандидат
   отклоняется, если отрезок заходит в запретную зону
   (`ObstacleIndex.isInteriorBlocked`), нарушает минимальный угол спецпрохода
   (`SpecialZoneIndex.angleOk`) или угол на стыке (`turnAllowed`). Остальная
   геометрия рёбер не меняется; канонический выход (`target`/`tail`) и хвост
   вывода сохраняются.
3. **Отбор и приём.** Кандидаты ранжируются по дешёвой локальной дельте
   стоимости стыков (`segmentCost` по фактическому Ду и `Kспец`); для лучшего
   выполняется `MaxLengthEnforcer.enforce` и полная оценка `estimateScore` —
   принимается только строгое улучшение с сохранением предельной длины. Порядок
   обхода камер детерминирован (id), проходов — `forest-chamber-passes` (1);
   деревья обрабатываются параллельно (ADR-0049).

## Следствия

- Положительные: основной набор `S` **13.5606 → 13.2279**, длина
  **1910.4 → 1859.8 м**; OSM (strict) `S` 13.5036 → 13.4463. Инварианты
  FR-26/FR-29/FR-34 и канонические выходы — без регрессий. Стадия дешёвая:
  ~36 мс (основной), ~1 с (OSM); общий расчёт не замедляется (стадия заменяет
  прежний `optimizeRoots` с gridPath-фолбэком и в сумме быстрее).
- Отрицательные/ограничения:
  - при включённой оптимизации камер флаг `forest-root-optimization` не
    используется: корень обрабатывается внутри `optimizeChambers` (проекции на
    сеть); при выключенной — старое поведение E35 сохраняется;
  - медиана считается в евклидовой метрике; перепрокладка только прямолинейная
    (без gridPath-обхода) — при заблокированном отрезке кандидат отклоняется,
    часть потенциальной экономии может не реализоваться;
  - жадный покомандный порядок и один проход — локальный оптимум.
- Затрагивает `GridForestPlanner` (`optimizeChambers`/`relocateChamber`/`stub`/
  `chamberCandidates`/`weightedMedian`), `AppProperties`/`application.yml`
  (`forest-chamber-optimization`, `-search-radius-cells`, `-max-candidates`,
  `-passes`), тесты (`ChamberOptimizationExperimentTest`,
  `CalculationPipelineSlowTest` baseline), `docs`.
